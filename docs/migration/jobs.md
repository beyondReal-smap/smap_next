> 총 **12개 잡**. Phase 3에서 asynq로 이전 (가장 큰 성능 이득 영역).

> **스케줄러 구성**: [스케줄러 구성] - 단일 in-process 스케줄러: app/core/scheduler.py의 BackgroundTasks가 apscheduler.schedulers.background.BackgroundScheduler 인스턴스 1개를 보유. 모듈 로드 시 전역 `scheduler = BackgroundTasks()` 생성. app/main.py:26에서 import, lifespan startup에서 scheduler.start() 호출. - 잡 등록: BackgroundTasks.__init__에서 더미 'background_task'(60초 interval, 로그만 출력)를 먼저 등록. start() 시 _jobs_scheduled 플래그로 _schedule_all_jobs()를 1회만 실행(중복 add 방지). - _JOB_REGISTRY는 _get_job_func 최초 호출 시 지연 import로 채워짐(순환 import 회피). _run_job(job_name)이 SessionLocal()로 DB 세션 생성 → thread-local self.db에 보관 → job_func(db) 실행 → finally에서 db.close() + 이전 세션 복원. 예외 시 db.rollback(). - APScheduler 옵션 표준값: 30초 잡=misfire_grace_time=25, 1분 잡=50, 20분 잡=300, cron 잡=3600. 전부 max_instances=1, coalesce=True. 따라서 같은 잡의 동시 중복 실행은 '동일 프로세스 내에서만' 차단되고, 밀린 미스파이어는 1회로 합쳐짐.  [등록된 잡 vs 미등록 함수 — 중요] - _schedule_all_jobs에 실제 add_job 되는 잡은 13종: 위치알림 4(30초), schedule_notification·send_reserved_push(1분), update_user_locations_every_20_minutes(20분), cron 5종(silent 03:00 / app_trigger 19:30 / low_battery 21:00 / weather_refresh 06:30 / weather_notify 07:00). - _JOB_REGISTRY에는 등록됐지만 _schedule_all_jobs에서 add_job 되지 않은(=실제 실행 안 되는) 함수: run_sync_member_locations_recently, run_force_update_internal_locations_midnight, run_send_daily_log_notifications, run_send_my_location_push_notifications, run_schedule_movement_alert. → location_sync의 sync_recently/force_midnight, daily_jobs의 log/my_location_push/movement_alert는 현재 트리거가 없음(데드 스케줄). Go 이식 시 활성/비활성 구분 필수. - auth_jobs.run_purge_expired_refresh_tokens는 _JOB_REGISTRY에도 _schedule_all_jobs에도 전혀 없음 → 스케줄러에 연결돼 있지 않음(정의만 존재). docstring상 '일 1회 야간 실행 권장'이나 실제 스케줄 미연결. Go 이식 시 신규 cron(예: daily 04:00, 'DELETE FROM refresh_tokens WHERE expires_at < now()-7d')으로 추가 필요.  [이중 실행 방지 메커니즘 — SMAP_DISABLE_SCHEDULER 정밀 기록] - 유일한 이중 실행 방지 수단은 환경변수 SMAP_DISABLE_SCHEDULER 1개. 분산 락(Redis/DB advisory lock), 리더 선출, DB 행 클레임 등은 코드 전반에 전혀 없음. - app/main.py:93 `_scheduler_disabled()` = `os.getenv("SMAP_DISABLE_SCHEDULER","").strip().lower() in {"1","true","yes"}`. 빈 값/미설정/그 외 문자열("0","false","off" 등)이면 비활성화로 보지 않음(즉 스케줄러 가동). - lifespan(main.py:104~122): startup에서 _scheduler_disabled()가 True면 scheduler.start()를 스킵하고 "Scheduler startup skipped" 로그만, False면 scheduler.start(). shutdown에서도 not _scheduler_disabled()일 때만 scheduler.shutdown() 호출. - 의도된 운용 모델: API 서버를 여러 프로세스/인스턴스로 띄울 때, 스케줄러를 돌릴 '단 하나의 프로세스'에만 SMAP_DISABLE_SCHEDULER를 비워두고(가동), 나머지 모든 프로세스에는 SMAP_DISABLE_SCHEDULER=1을 줘서 스케줄러를 끄는 방식. 즉 '운영자가 환경변수로 수동 단일화'하는 구조이며 자동 보장 장치가 아님. - 한계/위험: (1) 실수로 두 프로세스 모두 변수 미설정 시 두 스케줄러가 동시에 모든 잡을 실행 → 푸시/상태변경 잡 중복(특히 entry/exit/schedule_notification/reserved_push/일일 cron). APScheduler max_instances=1은 프로세스 경계를 넘지 못함. (2) start.sh는 --workers 없이 단일 uvicorn(--reload)으로 기동하므로 현재 단일 인스턴스 전제에선 안전하지만, 멀티워커(gunicorn -w N, uvicorn --workers N)나 수평 스케일 시 워커마다 BackgroundScheduler가 생겨 N배 중복 실행됨 → 이때 SMAP_DISABLE_SCHEDULER만으로는 워커 단위 제어가 불가(프로세스별 env 분리 어려움). 멀티워커 환경은 사실상 미지원.  [Go(asynq) 이식 권장 아키텍처] - 단일 in-process 스케줄러를 Redis 기반 asynq로 전환하면 이중 실행 문제를 구조적으로 해결: asynq Scheduler(엔트리 등록기)를 1개만 띄우고(또는 redis 분산 락으로 리더 1명 선출), 워커는 N개로 수평 확장해 잡 본문을 소비. SMAP_DISABLE_SCHEDULER 같은 수동 env 분리가 불필요해짐. - 30초/1분/20분 interval 잡: asynq의 PeriodicTask(robfig/cron 스펙) 또는 @every; 30초는 cron 표현 불가하므로 asynq Scheduler에 '@every 30s' 또는 ticker. - 멱등성 보강(핵심): 현행 entry/exit/my_place/schedule_notification/reserved_push는 'SELECT 후 발송 후 상태 UPDATE'의 check-then-act라 이중 실행/부분 실패에 중복 발송 취약. Go에서는 (a) 발송 권한을 'UPDATE ... SET 처리됨 WHERE 미처리' 조건부 UPDATE의 RowsAffected==1로 먼저 클레임 → 그 후에만 FCM 발송(claim-then-send), 또는 (b) reserved_push는 SELECT ... FOR UPDATE SKIP LOCKED로 행 임차. daily 전원 발송(low_battery/app_trigger/weather_notify/silent)은 일자 키 기반 asynq Unique(TaskID에 YYYYMMDD 포함) 또는 redis SETNX 분산 락으로 'daily 1회'를 보장. - 시간 의존(weather_refresh 06:30 → weather_notify 07:00)은 현재 cron 시각으로만 암묵 보장 → asynq 태스크 체이닝(refresh 완료 후 notify enqueue)으로 명시적 의존성 전환 권장. - 외부 의존은 FCM(firebase admin SDK Go: firebase.google.com/go/v4/messaging)과 KMA API(net/http, KMA_SERVICE_KEY 시크릿)로 매핑. 블로킹 푸시는 워커 동시성으로 처리하고 asynq 재시도/타임아웃 정책을 잡별로 설정.
